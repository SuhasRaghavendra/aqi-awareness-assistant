2. Problem Statement & Formulation

In India, regulatory CPCB (Central Pollution Control Board) stations measure air pollutants retrospectively. By the time a "Severe" AQI reading is published, vulnerable populations (asthmatics, elderly, children) have already suffered acute exposure, and city administrators cannot take preventive action.

This system operates in real-time at day $t$ to forecast conditions for day $t+1$:

  • Task A (Continuous AQI Regression): Predict the next-day continuous CPCB AQI value ($0 \le \hat{y}_{t+1} \le 500$) given observations up to day $t$.
  • Task B (CPCB Statutory Category Classification): Predict the statutory health hazard band: Good (0-50), Satisfactory (51-100), Moderate (101-200), Poor (201-300), Very Poor (301-400), and Severe (401-500).

3. Data Sourcing, Panel Construction & Zero-Leakage Controls

A machine learning model is only as good as its data integrity. The evaluators will likely ask: "Where did you get your data and how did you prevent data leakage?"

3.1 Data Sinks & Multimodal Sources

  • Air Quality Data (Ground Truth): CPCB CAAQM ground monitoring stations sourced via the verified XKDR Forum India AQI dataset. Provides clean daily station-level observations for all 9 cities.
  • Meteorological Reanalysis: ECMWF ERA5 reanalysis via Open-Meteo API. Extracted coordinate-based surface temperature (min/mean/max), relative humidity, precipitation, boundary layer wind speed, and surface pressure.
  • Satellite Fire Radiative Power (FRP): NASA FIRMS (MODIS / VIIRS active fire detections). Features computed within a 500 km radius of each city center (fire count, total FRP sum, and distance to nearest active fire cluster).
  • Socioeconomic & Policy Context: Delhi GRAP (Graded Response Action Plan) stages 0–4 calendar, statutory Indian national festival calendars (Diwali/monsoon flags), RBI Index of Industrial Production (IIP), and Ministry of Road Transport (MoRTH) vehicular fuel fraction shares.

3.2 Chronological Split vs. Random Split

Critical Concept: Why Random K-Fold CV is Catastrophic for Time-Series!
In air quality forecasting, neighboring days share high temporal autocorrelation (e.g. yesterday's AQI is highly predictive of today's AQI). If you perform a random train/test split, the model trains on Monday and Wednesday and tests on Tuesday. This is a severe future data leak that results in artificially inflated $R^2 > 0.95$ in papers that completely collapses in real deployment.

We enforced a strictly chronological, non-overlapping split (Architectural Decision Record D-004 and D-018):

  • Training Set: Inception to 2023-12-31 (Multi-year historical base: 14,000+ station-days).
  • Validation Set: 2024-01-01 to 2024-12-31 (Full 365-day annual cycle used for hyperparameter tuning, forward-chained calibration, and gate evaluation).
  • Holdout Test Set: 2025-01-01 to 2026-03-26 (1,852 rows across all 9 cities; untouched during modeling, evaluated strictly once).

3.3 Single Scaler Isolation (Zero Test Leakage)

Many ML pipelines mistakenly fit a StandardScaler on the entire dataset or refit separate scalers in training and evaluation scripts. We enforce a single fitted scaler:

  • Fitted strictly on train.parquet during src/features/build_features.py.
  • Saved as an immutable artifact data/processed/scaler.joblib.
  • Loaded identically by src/models/train.py, src/models/evaluate.py, and the production FastAPI inference engine.
  • Verified by our automated integrity audit: scaler.mean_matches_a_fresh_train_fit == 0.0.

5. Modeling Decisions & The Residual Monotone Breakthrough

The "Persistence Defeat" Trap (Why most air quality models fail in industry):
In air quality forecasting, today's AQI is an extremely strong predictor of tomorrow's AQI. The naive persistence heuristic ($\hat{y}_{t+1} = y_t$) achieves an impressive $R^2 \approx 0.86$ and $\text{MAE} \approx 14.5$. When standard direct regressors (Ridge, Random Forest, XGBoost) are trained to predict raw tomorrow AQI, they consistently lose to persistence because their gradients smooth out sharp transitions!

5.1 The Solution: Persistence-Anchored Residual Modeling

Instead of tasking the learner with predicting absolute AQI level, we reformulated the objective:

$\text{Target} = y_{t+1} - y_t \quad (\Delta\text{AQI})$
$\hat{y}_{t+1} = y_t + \hat{\Delta}_{\text{model}}$

By anchoring the prediction to current AQI ($y_t$), the machine learning model focuses 100% of its capacity on learning the rate of atmospheric change driven by weather dispersion, wind shifts, and fire surges.

5.2 The Metamorphic Flaw & Monotone Constraints

When unconstrained decision trees (GBDT) are trained on tabular data, splits are made greedily. On holdout tests, an unconstrained tree can evaluate a counterfactual scenario with 5,000 active fires and predict a lower AQI than a scenario with 0 fires simply because of a spurious leaf split on a collinear feature!

To eliminate this, we implemented Monotone Constraints in LightGBM (Architectural Decision Record D-030):

  • Positive Monotonicity ($+1$): fire_count_500km, fire_frp_sum_500km, fire rollings, fire lags, fire_x_low_wind, inversion_x_fire. Constraint: As fire activity increases, predicted AQI must never decrease.
  • Negative Monotonicity ($-1$): wind_speed_10m_mean, wind lags, wind rollings. Constraint: As wind speed increases (improving ventilation), predicted AQI must never increase.

7. Model Registry & The Byte-Stable Champion Bundle

Models are logged and tracked via MLflow 3.17. Instead of deprecated staging tags (Staging/Production), we use modern MLflow Aliases: @challenger and @champion.

7.1 The Byte-Stable Champion Bundle Format 1.1

In production, relying on dynamic MLflow database connections can fail due to network drops or SQLite locks. We package the champion model into an atomic, standalone directory committed to Git at artifacts/champion/:

  • bundle.joblib (878 KB): Serialized model, fitted StandardScaler, 103 feature names, residual quantiles (10th, 50th, 90th) for confidence interval calculation, and per-city calibration offsets.
  • history_seed.parquet (162 KB): Seed rows containing the last 45 days of observations for each of the 9 cities (405 rows total). This allows the service to boot from scratch and compute lags immediately without requiring a database warm-up!
  • reference_stats.json (21 KB): Mean, standard deviation, and quantile distribution for all 103 features calculated exclusively from the training set (used for live drift detection).
  • MANIFEST.json & MANIFEST.sha256: Machine-readable specification recording exact SHA-256 digests of all bundle contents, git commit SHA, data MD5, gate results, and feature count.

7.2 Security Chain of Custody: Hash Verification Before Unpickling

Python's joblib.load() or pickle.loads() execute arbitrary bytecode. If a model file is corrupted or maliciously altered on disk, unpickling it creates an immediate Remote Code Execution (RCE) vulnerability. Our custom AqiBundle.load(verify=True) executes a strict three-tier cryptographic check:

MANIFEST.sha256  ──[Assert Match]──>  MANIFEST.json  ──[Assert Match]──>  bundle.joblib (Loaded ONLY if hash verified!)

8. Production FastAPI Serving Engine

The inference service lives in src/service/ and is built on FastAPI + Uvicorn.

8.1 Eliminating Training-Serving Skew

The most common bug in machine learning production is Training-Serving Skew (where data preprocessing in Python during training is re-implemented differently in JavaScript, C++, or another serving module). We eliminated this entirely: both offline DVC feature engineering and the online FastAPI service import the exact same pure functions from src/features/serving_features.py!

9. Docker Containerization & Security Hardening

The inference service is packaged in a production-hardened multi-stage Dockerfile based on python:3.12-slim-bookworm.

9.1 Multi-Stage Build Efficiency

  • Stage 1 (Builder): Installs build compilers (build-essential, libgomp1) and compiles Python wheels from requirements-serve.txt into /build/wheels.
  • Stage 2 (Runner): A clean, minimal image that copies wheels from the builder and installs them with --no-index. Compilers, build caches, and package managers are excluded from the final image, reducing image size to 362 MB (well under the 500 MB budget).

9.2 Non-Root Execution (Defense-in-Depth)

Running containers as root (UID 0) is a major security risk. In our container:

  • A dedicated system user is created: groupadd -g 10001 appgroup && useradd -u 10001 -g appgroup -m appuser.
  • All application files are chowned to appuser:appgroup.
  • The container explicitly drops privileges: USER appuser (UID 10001).

9.3 Security Vulnerability Gate (Zero CVEs)

During CD, the container is scanned using Aqua Security Trivy. When an upstream vulnerability was detected in pyarrow==22.0.0 (CVE-2026-25087 - High Severity), we immediately upgraded to pyarrow==23.0.1 in both requirements files, achieving a completely clean vulnerability scan: 0 Critical, 0 High.

10. GitHub Actions CI/CD Pipeline

The repository enforces continuous integration and continuous delivery via two automated workflows:

10.1 CI Workflow (.github/workflows/ci.yml)

Triggered on every Pull Request and push to main across 7 parallel jobs:

  1. lint: Enforces PEP-8 code styling via ruff check and black --check.
  2. unit: Executes 174 fast unit tests across data modules and utility functions.
  3. model-gate: Validates that the champion bundle passes all metamorphic, determinism, and quality gates.
  4. registry: Spawns a temporary SQLite tracking store, registers the bundle, loads models:/Indian-AQI-Predictor@champion, and asserts $1 \times 10^{-6}$ mathematical parity against the offline bundle.
  5. service: Boots the FastAPI test client and verifies latency budgets and schema contracts.
  6. docker: Builds the container from scratch and runs scripts/test_container.sh.
  7. dvc-consistency: Verifies dataset reproducibility against remote DagsHub storage when credentials exist.
The Broken-Model PR Test: To prove our branch protection works, we opened a test PR (branch test/broken-model-gate) containing an intentionally corrupted model that violated the metamorphic fire direction. GitHub Actions model-gate automatically failed and blocked the PR from merging!

10.2 CD Workflow (.github/workflows/cd.yml)

Triggered whenever a semantic version tag (e.g. v1.0.2) is pushed:

  1. Builds the Docker container via Buildx.
  2. Runs Aqua Trivy vulnerability scanner (fails if any fixable Critical/High CVE is found).
  3. Pushes multi-tagged container images to GitHub Container Registry (GHCR): latest, v1.0.2, and commit-pinned sha-<commit>.
  4. Render automatically detects the updated image and redeploys without downtime.

11.2 The Production Runbook (Drift & Retraining Protocol)

Documented in docs/RUNBOOK.md:

  • Feature Drift Detection (PSI): Population Stability Index computed over a rolling 500-request window against reference_stats.json.
    $\text{PSI} < 0.1$: Normal fluctuation.
    $0.1 \le \text{PSI} \le 0.2$: Moderate shift (log warning).
    $\text{PSI} > 0.2$: Significant feature drift (triggers P1 retraining alert).
  • Realized Accuracy Degradation: 14-day rolling realized MAE monitored against the baseline validation MAE ($13.23$). If rolling MAE exceeds $1.5 \times 13.23 = 19.85$, trigger automated retraining.
  • One-Click Instant Rollback: If an incident occurs, administrators can change the Render container image tag in 1 click from :latest back to any stable commit SHA tag (e.g. :sha-11cd466), restoring previous verified service in < 20 seconds.

12. Master Evaluator Q&A (The Defense Bible)

Here are the exact technical questions evaluators are most likely to ask, along with comprehensive, bullet-proof answers:

Q1: "Why did you use LightGBM instead of an LSTM, GRU, or Transformer for time-series forecasting?"
Answer: "We considered Deep Learning architectures (LSTM/Transformers), but empirical research on tabular time-series panels (e.g. Grinsztajn et al., NeurIPS 2022) demonstrates that gradient-boosted decision trees consistently outperform deep networks on tabular data with heterogeneous numerical and categorical features. Furthermore, LSTMs require extensive sequence padding, are vulnerable to irregular sensor dropouts, have significantly higher inference latency (>100ms vs our 11ms), require 10x more training data, and cannot easily support strict physical monotonicity constraints. LightGBM enabled exact directional monotonicity on fire/wind features while easily beating persistence in under 15ms."
Q2: "What is data leakage and how did your architecture guarantee zero leakage?"
Answer: "Data leakage occurs when information from the target or test distribution inadvertently enters the training phase. We prevented leakage across three architectural layers: 1. Temporal Split: We strictly used a chronological split (Train $\le 2023$, Val $2024$, Test $2025+$) rather than random K-Fold. 2. Lag & Rolling Shifts: Every lag and rolling feature (e.g. aqi_roll_mean_7d) is strictly shifted by 1 day so day $t+1$'s target is never visible during feature aggregation. 3. Scaler Isolation: The StandardScaler was fitted exclusively on the training split, saved to disk, and reused as an immutable object during validation, test, and live inference."
Q3: "What is the difference between your /health and /ready endpoints?"
Answer: "In Kubernetes and modern cloud PaaS architectures, liveness and readiness serve completely different operational purposes: - /health is a Liveness Probe. It tests whether the Python Uvicorn process is alive and accepting TCP sockets. If it returns non-200, the container orchestrator immediately kills and restarts the container. - /ready is a Readiness Probe. It tests whether the machine learning model artifact, fitted scaler, and 45-day history seed have finished deserializing into RAM. If /ready returns 503, the load balancer keeps the container alive but does not route client traffic to it until it is fully warmed up."
Q4: "Why did you containerize with a non-root user (UID 10001) instead of standard root?"
Answer: "Running container processes as root (UID 0) violates the principle of least privilege. In the event of a container breakout vulnerability (e.g. CVE in the Linux kernel or container runtime), a root process inside the container can potentially gain root access to the host virtual machine. By enforcing a dedicated non-root user appuser:appgroup (UID 10001), even if an attacker achieved code execution, their capabilities are strictly bounded inside the unprivileged namespace."
Q5: "How does your system handle missing sensor features when a user queries the live API?"
Answer: "The service requires only 3 inputs from the caller: city, date, and today's aqi. If meteorological or fire variables are omitted, the server automatically imputes them using the precomputed training median from reference_stats.json. For historical lags, the server consults its in-memory 45-day history seed (pre-seeded from history_seed.parquet), seamlessly maintaining continuous rolling windows."
Q6: "What is Metamorphic Testing and why is it superior to traditional unit testing for ML?"
Answer: "Traditional unit tests check whether a given input produces an exact pre-calculated output (an oracle). But in ML, you don't always know what the exact output AQI should be for an unseen day. Metamorphic testing tests relational properties: if we take any valid day's input and increase upstream satellite fires by $5\times$, physical domain laws dictate that predicted AQI must either increase or stay constant—it must never drop. Our metamorphic suite perturbs raw inputs, rebuilds all 103 features, and asserts a non-monotone rate $\le 5\%$. Our champion achieved a perfect $0.0\%$ non-monotone rate."
Q7: "How do you detect when your deployed model needs to be retrained?"
Answer: "We monitor two continuous signals: 1. Input Data Drift: We calculate the Population Stability Index (PSI) over a rolling 500-request window against reference_stats.json. If PSI exceeds 0.2, an alert flags that input distributions have drifted significantly. 2. Realized Prediction Error: As clients report actual AQI for day $t$ when querying day $t+1$, we track a rolling 14-day MAE. If realized MAE exceeds $1.5\times$ our validation baseline ($> 19.85$ AQI points), a P1 alert triggers our standard automated retraining pipeline (dvc repro followed by our 5 automated quality gates)."
Q8: "Why does the live API return degraded: true and a warning about historical gaps?"
Answer: "The champion bundle's frozen history seed contains regulatory CPCB data up to March 2026. When a user requests a prediction for a future date (e.g. November 2026), there is a multi-month calendar gap between the end of the frozen seed and the requested date. Instead of crashing, the service gracefully median-fills the intermediate lags, serves the forecast, and attaches degraded: true and an informative warning in the JSON response. This provides production resilience while maintaining absolute transparency with the client."
Q9: "How do you ensure reproducibility across different developer machines?"
Answer: "We enforce reproducibility through five distinct tools: 1. DVC (Data Version Control): Hashes every stage's inputs and outputs in dvc.lock, backed by remote DagsHub storage. 2. Git Commit Lineage: Every model artifact, manifest, and MLflow run is tagged with the exact Git commit SHA. 3. Data-Derived Timestamps: Artifact creation timestamps are derived from the newest dataset observation (not wall-clock time), making repeated builds byte-identical. 4. Pinned Dependencies: Exact package versions are pinned in requirements.txt and requirements-serve.txt. 5. Docker: The multi-stage container ensures the exact same runtime environment in local testing, GitHub Actions runners, and Render cloud servers."
